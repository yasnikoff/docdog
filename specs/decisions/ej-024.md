# dd_ System Namespace and User Namespace Separation

Two namespaces coexist in each project database:

## System Namespace (dd_ prefix)

System collections are docdog machinery — never user content:
- `dd_patches` — proposed changes to sections (EJ-014 tier 3)
- `dd_edges_structural` — parent/child, index membership
- `dd_edges_semantic` — references, companion, uses_term
- `dd_edges_temporal` — supersedes, revised_by
- `dd_edges_dependency` — constrains, implements
- `dd_edges_crosscutting` — sourced_from, cross_cutting
- `dd_embedding_cache` — keyed by content hash (EJ-015)

The `dd_` prefix is a contract: docdog owns these, users don't modify them. Defined as
frozen constants in `src/arango/collections.ts`.

## User Namespace (no prefix)

User content collections have no prefix. They are declared per-project in
`.docdog/config.yaml` under `vertex_collections`. Examples: `decisions`, `notes`,
`principles`, `guidelines`.

## default_collection

The `default_collection` config field names a catch-all collection for files that
can't be routed via frontmatter `collection:` field or directory name inference.
Must be a member of `vertex_collections`. If not set, unroutable files are skipped
with a warning.

## Why dd_ (Not _system or system:)

- `_` prefix is reserved by ArangoDB for its own system collections
- `system:` contains a colon which is invalid in ArangoDB collection names
- `dd_` is short, unlikely to collide with user names, and sorts predictably
- Open question (OQ-25): investigate `isSystem: true` flag for deeper integration

## Rationale

Clean separation between platform infrastructure and user content. Users never
accidentally modify system collections. System collections are always discoverable
by prefix. User collections are fully customizable via config (EJ-021).
