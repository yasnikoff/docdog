# Database Naming and Project Templates

## Database Naming

Each project gets its own ArangoDB database named `docdog_{project_name}`. The prefix
is a constant (`DEFAULT_ARANGO_DB_PREFIX = "docdog_"`) in `src/config/defaults.ts`.

Examples:
- `docdog_docdog` — docdog managing its own docs (dogfooding)
- `docdog_orchestrator` — the orchestrator project
- `docdog_my_app` — a user project named "my-app"

## Project Templates

`docdog init --template <name>` scaffolds the project with a predefined collection set:

### minimal (default)

```yaml
vertex_collections: [notes]
default_collection: notes
```

For projects that just need a searchable knowledge base. One collection, zero decisions
about taxonomy. Users can add more collections later via config (EJ-021).

### orchestrator

```yaml
vertex_collections:
  - decisions
  - requirements
  - principles
  - guidelines
  - terms
  - domain
  - constraints
  - integrations
  - notes
default_collection: notes
```

For projects with structured documentation: design decisions, requirements, glossary
terms, etc. Mirrors the document types in the Orchestrator's spec library.

## Rationale

Database-per-project gives clean isolation — `arangodump` backs up one project without
touching others. The `docdog_` prefix makes databases discoverable in ArangoDB UI.
Templates lower the init friction: minimal for exploration, orchestrator for real projects.
Both include `notes` as the default collection so unroutable files always have a home.
