# Features Are DB-First; Templates Are User-Owned Scaffolding

Two related commitments in one decision, because they're usually entangled in
discussion and clearer together.

## Features are DB-first

The `features` collection (shipped in the `workflow` template) is created via
`docdog_create`, updated via `docdog_update`, and rendered to disk via a
`render-matrix` script that produces `specs/features.md`.

No source markdown files for features. No disk-first indexing. The markdown
snapshot is derivative.

**Rationale:**
- Status churns fast (multiple transitions per day on active work).
  Disk-first means an edit + re-index cycle per transition — friction
  that compounds.
- Features sit between normative specs (stable, disk-first) and working
  context (ephemeral, DB-only). The DB-first pattern fits the middle tier.
- `specs/features.md` carries a `do not edit` header and is idempotently
  overwritten. No round-trip sync concerns.

## Templates are user-owned scaffolding

Docdog ships three templates (`minimal`, `structured`, `workflow`). Each bundles
a set of collections, default skills, and optionally starter scripts. On
`docdog init`, the template contents are copied into the user's project.

**From that point forward, templates are seed content owned by the user.**
Docdog core:
- Never reads from `tasks/`, `features/`, or `conversations/` collections
  (only the user's skills do)
- Never enforces workflow semantics — status vocabulary is a string, state
  transitions are user-decided
- Never auto-syncs template content after init (opt-in via `docdog templates refresh`)

The EJ-030 test still holds: delete every skill in `.docdog/skills/`, docdog
still works as a memory layer. The workflow template is an example, not a
product.

## Risks acknowledged

- **Scaffolding drift.** A user's `.docdog/skills/` can diverge from docdog's
  shipped templates over time. That's expected. Users who customize own the
  divergence.
- **Opinionated defaults.** Shipping ~14 skills in the workflow template is
  more opinionated than `minimal`. Users who want less can pick a smaller
  template or delete skills after init.
- **Salvageable.** If docdog's core ever regrets shipping workflow skills,
  the workflow template can be extracted into a separate `@yasnikoff/docdog-workflow`
  package that hard-depends on docdog core. The code is decoupled enough to
  support this.

## Rationale summary

Features as DB-first is the right model for their access pattern (high churn,
dynamic state). Templates as user-owned is the right framing per EJ-030 (docdog
is memory, not orchestration). Both commitments keep docdog core honest while
giving users a concrete starting point for structured-specs projects.
