# Two-Tier Content Model — Published Specs vs Working Context

## Published Specs

Decisions, requirements, principles, guidelines, terms, constraints.

- Live in both ArangoDB and on disk (bidirectional sync)
- Committed to git — readable by humans and non-docdog agents
- Created via: edit file + index (human path) OR MCP tool + export (agent path)

## Working Context

Refinements, discussions, conversations, drafts, notes.

- Live in ArangoDB only — no disk files in the repo
- Searchable via MCP tools, not by browsing the filesystem
- Created via: MCP tools (direct to DB) or one-time ingest

## Agent Workflow

When docdog is installed, agents always go through ArangoDB. There is no valid
scenario where a docdog skill should tell an agent to write a file first — if
docdog is installed, ArangoDB is available. If not installed, skills aren't either.

## On-Disk Files Serve As

1. Git-committed documentation (for humans, code reviewers, non-docdog agents)
2. Backup/snapshot of ArangoDB state
3. Import source for hand-edited content (indexer picks up changes)
4. Graceful degradation when ArangoDB is unavailable

## Implications (Not Yet Implemented)

- Collection config needs `export: true/false` field (OQ-31)
- Need `docdog_create` / `docdog_update` MCP tools (OQ-32)
- Need `docdog export` for DB→disk sync
- Refinements ingest directly to ArangoDB, not into repo files (OQ-33)

## Rationale

Refinement sessions are valuable agent context but not normative documentation.
Putting them in the orchestrator repo would be noise for readers and unmaintained
artifacts. The DB-only tier keeps the repo clean while preserving full searchability
through the graph.
