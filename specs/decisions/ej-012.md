# AI-First Interface — Provider-Neutral Skills in .docdog/

The primary interface to docdog is AI-first. The MCP server provides provider-agnostic
tool access (any MCP-compatible agent can call `docdog_search`, `docdog_traverse`).
Skills are orchestration workflows defined as provider-neutral markdown in
`.docdog/skills/` — structured enough for any LLM to follow.

## Skill Storage

```
.docdog/
├── config.yaml              <- connection, collections, scan paths
├── skills/                  <- provider-neutral skill definitions (source of truth)
│   ├── fetch.md
│   ├── refine.md
│   ├── index.md
│   ├── relate.md
│   └── audit.md
└── providers/               <- thin injection adapters
    ├── claude/
    ├── cursor/
    └── ...
```

## Subagent Model

A skill markdown IS the subagent's prompt. The calling agent spawns a subagent with
the skill definition as instructions + the user's query as input. The subagent has MCP
tools available and follows the steps.

## MCP Resource Discovery

The MCP server exposes skill definitions as MCP resources (read-only). An agent without
`.docdog/skills/` in its context can still discover what docdog can do by reading the
resource list.

## Rationale

Low learning curve for humans (talk to the AI, it knows the tools). Provider-agnostic
by default (skills are markdown, not .claude/ commands). Subagent model is the natural
fit for context fetching — don't pollute the main agent's context with search internals.
