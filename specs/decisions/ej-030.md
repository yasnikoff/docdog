# Docdog Is a Memory Layer, Not a Workflow Engine

Docdog core provides primitives for storing, searching, and traversing documentation
content. It does not ship workflows, enforce lifecycles, or manage processes. These
belong to users.

## Three Layers

1. **Core primitives** (docdog owns) — vertices, edges, search, traverse, CRUD,
   indexer, embedder, GC, MCP tools, CLI. The only required layer.
2. **Default skills** (docdog ships, user owns) — `search.md`, `relate.md`,
   `populate.md`, `ingest.md`, `index.md`. Copied to `.docdog/skills/` on init.
   Fully replaceable.
3. **User skills/workflows** (user owns completely) — project-specific workflows,
   custom scripts, patches to default skills.

## The Test

A project using only docdog core primitives and its own skills must be fully
functional. If a user cannot delete every default skill and replace them with
their own, docdog has overreached.

## System Collection Scope

`dd_` prefix is reserved for docdog operational machinery only
(`dd_embedding_cache`, `dd_meta`, `dd_edges_*`). Collections named after workflow
concepts (`tasks`, `conversations`, `discussions`, `refinements`, `patches`) are
user collections with no docdog-enforced semantics.

## Implications

- `conversations`/`discussions` (OQ-27/28) → user collections, not `dd_*`
- `dd_patches` (OQ-26) → reconsider as user collection `patches`
- EJ-029 agent workflow claim is softened: "agents use MCP tools when available;
  user workflows must function without docdog"

## Rationale

Docdog's value is memory, not orchestration. Users need flexibility to define
their own workflows. Workflow concepts baked into core freeze assumptions that
won't fit every project.
