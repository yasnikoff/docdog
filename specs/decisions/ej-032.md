# Multi-Section Files Stay Minimal on Disk

When a user keeps multi-section files (indexed via the split parser), per-section
metadata on disk is limited to what the parser extracts: `id`, `title`, `status`,
`date`.

## What Stays in ArangoDB Only

- Agent-authored `description` fields (added via `docdog_update`)
- Relationship edges (via `docdog_relate`)
- Any other enriched fields

The file on disk stays as the user wrote it. Re-indexing never writes back. A human
reading the file does not see agent enrichment; a query via MCP/CLI does.

## The Explicit Tradeoff

| You want | Do this |
|---|---|
| Keep existing multi-section files | Parser hints, limited disk metadata, rich DB metadata |
| Rich per-section metadata on disk | Split into one-file-per-section |

## Why No Per-Section Frontmatter Convention

Considered and rejected:
- **Extending split parser with more inline patterns** — heuristic and fragile
- **Inline HTML comments with structured metadata** — ugly, non-standard
- **YAML frontmatter blocks between sections** — breaks markdown parsers

## Rationale

The user's writing experience wins. Multi-section files are authored by humans
writing prose; inventing metadata conventions would degrade that experience. The
DB-only path preserves richness where docdog owns storage; the split-file path
preserves richness where the user owns storage. Users pick explicitly.
