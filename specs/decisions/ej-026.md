# Forward-Only Migrations With Version Integer in Config

## Version Scheme

Single monotonic integer in `.docdog/config.yaml`:
```yaml
version: 1
```

- Pre-existing projects without version field = version 0
- Fresh `docdog init` sets LATEST_VERSION (no migrations needed)
- Each migration targets a specific version number

## Migration Interface

```typescript
interface Migration {
  version: number;
  description: string;
  up(ctx: MigrationContext): Promise<MigrationResult>;
}
```

Context provides:
- `rawConfig` (untyped Record — old schemas may not match current types)
- `db` (nullable — ArangoDB might be down)
- `projectRoot` and `configPath`

Result reports whether re-indexing is needed.

## Runner Behavior

1. Read version from config (0 if absent)
2. Filter registry for pending migrations (version > current)
3. Try connecting to ArangoDB (non-fatal if unavailable)
4. Apply each migration in order, write config after each (crash-safe)
5. Update dd_meta audit trail in ArangoDB (non-fatal if unavailable)

## State Tracking

- **Config version** — source of truth. Updated after each successful migration.
- **dd_meta collection** — audit trail only. Stores migration history with timestamps.
  Informational, not load-bearing.

## CLI Integration

- `docdog migrate` — run pending migrations explicitly
- `docdog migrate --dry-run` — show what would run
- Pre-action hook on all other commands warns if config is outdated (non-blocking)
- Commands `init`, `migrate`, `infra` skip the version check

## Key Design Choices

- **No rollback.** Git handles config rollback. ArangoDB backup handles data. Maintaining
  `down()` methods isn't worth it for a local-first tool.
- **rawConfig is untyped.** Migrations operate on old schemas — the current DocdogConfig
  interface might not match. This is intentional.
- **DB is nullable.** Config-only migrations work when ArangoDB is down. DB-dependent
  migrations skip gracefully and re-attempt on next run.
- **Forward-only integer** avoids semver complexity. Config + DB evolve together.

## Rationale

Most docdog "migrations" are just "re-index after updating code" — vertices are derived
from source files. The migration system handles the cases that re-indexing can't: config
schema changes, edge data transforms, and new system collections. Minimal base that's
hard to redesign: version scheme, migration interface, state tracking location.
