# One Section = One File, With Index Files Linking Sections

On-disk structure: each section is a separate markdown file with its own frontmatter.
An index file groups sections and carries group-level metadata.

```
specs/decisions/
├── architecture.index.md          ← index: frontmatter + links to sections
├── architecture/
│   ├── dd-arch-09.md              ← section: own frontmatter (id, status, related)
│   ├── dd-arch-10.md
│   └── ...
```

## Key Properties

- **Mandatory structure.** Even small files follow this pattern. Simplifies the indexer.
- **Frontmatter is the metadata contract.** Section frontmatter carries id, status,
  related requirements. No heading parsing, no guessing. Author-controlled metadata.
- **Mapping to Arango.** One section file = one Arango vertex. The `source_file` field
  on the vertex points to the section file.

## Rationale

One file per section means git merge conflicts are nearly impossible (two branches
must modify the exact same decision file). Frontmatter as metadata source eliminates
brittle heading-parsing heuristics. Mandatory structure means the indexer has one
code path, not special cases.
