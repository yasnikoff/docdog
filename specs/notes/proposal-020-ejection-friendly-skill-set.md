# PROPOSAL-020: Ejection-friendly injectable skill set

**Status note (2026-07-11, FEATURE-002):** shipped, two of three —
v3's `docdog skill install` (DD-070 §4) emits `navigate-specs` and
`specs` with exactly the delegation factoring this proposal argued
for. `/backport` was never built: it depended on PROPOSAL-021's
sync-policy/export bridge, which the v3 pivot superseded. The
DD-049 soft-delete framing referenced below is v2-era — v3 uses
DD-070's delete-the-file model.

## Motivation

PROPOSAL-019 introduced the injectable-skills mechanism with `/specs`
as the only registered name. The host-project orchestrator sidecar
planning then surfaced a stronger requirement: docdog adoption must
preserve a clear ejection path. The host repo cannot become
**trapped** by docdog — neither by the runtime depending on Arango,
nor by the on-disk artifacts becoming unreadable when docdog is gone,
nor by orchestrator-side skills accumulating docdog-specific
conventions that rot when docdog evolves.

The single-skill `/specs` design from PROPOSAL-019 covers the first
two requirements but not the third. Every host-repo skill that
references docdog conventions (frontmatter shapes, edge types,
status vocabulary) ends up duplicating that knowledge inline. When
docdog evolves, every host-repo skill goes stale independently.

This proposal **factors the conventions out of `/specs`** into a
separate skill `/navigate-specs`, and adds a third skill `/backport`
for the orchestrator's specific use case of processing backport
entries from completed tasks into canonical upstream-context
content. The factoring is deliberate: the three skills have
**distinct sources of churn** and **distinct ejection profiles**.

## Why three skills, not one

| Skill | What it knows | Source of change | Per-repo? | Ejection profile |
|---|---|---|---|---|
| `/navigate-specs` | docdog conventions: frontmatter fields, edge types, how to follow relations, how to retrieve historical content from git | docdog version | No, generic | Standalone markdown; teaches both docdog-MCP and grep+git fallbacks |
| `/specs` | This corpus's id prefixes, scan paths, file conventions, where the index lives | The host repo's content | Yes, generated per repo | Standalone markdown + a generated flat index file; agents grep the index when MCP is unavailable |
| `/backport` | This repo's backport workflow id, script name, target-field → canonical-path routing table | The host repo's `.docdog/workflows/` and `.docdog/scripts/` | Yes, generated per repo | Standalone markdown describing both `docdog workflow step` and the equivalent manual procedure |

Three skills, three churn sources, three ejection profiles. Collapsing
them produces inevitable rot — when docdog adds a new edge type, a
single-skill design forces every per-repo `/specs` regeneration to
re-encode the new convention; the factored design only requires
regenerating `/navigate-specs`, while the per-repo skills are
unchanged.

## Specification

### 1. Three registered injectable skills

```ts
export const REGISTERED_INJECTABLE_SKILLS: Record<string, string> = {
  "navigate-specs": "templates/injectable-skills/navigate-specs.md",
  "specs":          "templates/injectable-skills/specs.md",
  "backport":       "templates/injectable-skills/backport.md",
};
```

Each name maps to a template under `templates/injectable-skills/`.
The CLI surface from PROPOSAL-019 (`docdog skill install <name>`)
is unchanged — only the name registry grows.

### 2. Per-skill placeholder profiles

Each skill has a different set of valid placeholders. The renderer
in `src/engine/skill-install.ts` is extended to declare which
placeholders are valid per skill, and to reject templates that
reference an unknown one (defensive, beyond the existing
"unresolved placeholder is an error" check).

| Skill | Placeholders |
|---|---|
| `navigate-specs` | `{{docdog_version}}`, `{{generated_at}}` |
| `specs` | `{{id_prefixes}}`, `{{file_conventions}}`, `{{index_path}}`, `{{docdog_version}}`, `{{generated_at}}` |
| `backport` | `{{docdog_version}}`, `{{generated_at}}` |

The discovery functions for the three skills do different work:

- `navigate-specs`: no corpus discovery. Pure version + timestamp
  stamping. Fastest to render. Ships once per docdog version bump.
- `specs`: corpus discovery (id prefixes, scan paths) — same as
  PROPOSAL-019 §4 today.
- `backport`: no corpus discovery, no config reading at install
  time. Same shape as `navigate-specs` — pure version + timestamp
  stamping. The skill body points at the live
  `.docdog/config.yaml backport.*` block and instructs the agent
  to read it at run time. This keeps the skill reusable across
  projects and across workflow/routing changes without
  re-installation.

### 3. `/navigate-specs` content shape

The skill is a single markdown file describing **how docdog-managed
docs are organized**, in terms an agent can act on with or without
docdog running. Sections:

- **Frontmatter conventions** — the standard fields docdog stamps
  on vertices (`id`, `collection`, `title`, `status`, `description`,
  `relationships`), what each one means.
- **Relationship encoding** — how `relationships:` blocks express
  edges, the difference between `references` / `implements` /
  `supersedes` / `part_of` / `depends_on` / `cross_cutting`.
- **How to follow a relation without docdog** — given a vertex with
  `relationships: - implements: FR-PROV-06`, how to find the target:
  grep for `^id: FR-PROV-06\b` across the configured scan paths.
- **How to retrieve historical content from git history** — the
  `git log --diff-filter=D --name-only -- "tasks/TASK-NNN/*"` →
  `git show <commit>^:tasks/TASK-NNN/<file>` recipe, written out
  step by step. This is the ejection path for completed tasks per
  the orchestrator's existing folder-deletion behavior.
- **How to use docdog when present** — the MCP tools available
  (`docdog_search`, `docdog_get`, `docdog_traverse`, `docdog_relate`,
  `docdog_status`), what each returns, when to use which.
- **Footer** — docdog version + generation timestamp.

The content is hand-authored once in the docdog repo, lives at
`templates/injectable-skills/navigate-specs.md`, and is regenerated
verbatim on every `docdog skill install navigate-specs --force`. A
docdog version bump that changes conventions edits the template here
and re-installs in the host repo.

### 4. `/specs` refinement

The existing `/specs` template (PROPOSAL-019 §3) is refined in two
small ways:

- **Cross-references `/navigate-specs`** at the top — first thing
  agents read is "for docdog conventions and the relation-following
  recipe, see `./navigate-specs.md`. This file describes only the
  id prefixes and scan paths specific to this repo."
- **Drops any inline restatement of frontmatter / edge conventions**
  it currently has (or would have had — the PROPOSAL-019 v1 template
  is short enough that there isn't much to drop, but the refinement
  ensures `/specs` stays focused on per-corpus content and never
  duplicates `/navigate-specs`).

`/specs`'s content remains: the per-corpus id prefix list, the
scan-paths file conventions table, a pointer to the flat index
file, and a brief MCP cheat sheet. Same shape, smaller scope.

### 5. `/backport` content shape

The skill is **generic** — zero per-repo substitutions beyond
`{{docdog_version}}` and `{{generated_at}}`, same shape as
`/navigate-specs`. It does not bake workflow id, script name, or
routing table into the file at install time. Instead, the skill
body **points at the live `.docdog/config.yaml backport.*` block**
and instructs the agent to read it at run time. This keeps the
skill valid across workflow renames, routing changes, and reuse
across multiple projects — no re-installation required when host
config shifts.

Sections of the skill:

- **What a backport entry is** — the per-task
  `tasks/TASK-NNN/backport.md` shape: frontmatter with type / refs /
  target / upstream-version, body with the rationale.
- **How to find the live configuration** — explicit instruction:
  read `.docdog/config.yaml` and look for the top-level `backport:`
  block. It contains `workflow` (id), `script` (name), and
  `routing` (target → canonical path map). If the block is missing,
  stop and tell the user the repo has no backport configuration;
  do not guess.
- **The docdog-driven path** — once the agent has read the config,
  invoke `docdog workflow step <workflow-from-config>`. The
  workflow walks unprocessed entries one at a time, pauses at each
  for HITL review, applies on accept, deletes the source on
  success.
- **The manual / ejected path** — for each pending entry: read the
  backport.md, look up the `target:` field in the config's routing
  map, open the canonical file at the mapped path, integrate by
  hand, delete the source. Same conceptual work as the docdog
  path, no workflow gates.
- **What `/backport` does NOT do** — bookkeeping like LAST-BACKPORT,
  VERSION, MANIFEST-HASH (those are obsolete in the docdog model
  per the orchestrator-sidecar reframe).
- **Footer** — docdog version + generation timestamp.

The `backport:` config block schema lives in this repo (defined in
`src/types/config.ts`, shipped with the code) so both docdog and
the skill reference a single source of truth. Expected shape:

```yaml
backport:
  workflow: WF-O-001
  script: process-backport
  routing:
    design/decisions: specs/upstream-context/design/decisions/
    requirements:     specs/upstream-context/requirements/
    constraints:      specs/upstream-context/constraints/
    goals:            specs/upstream-context/goals/
```

`docdog skill install backport` does **not** validate this block at
install time — install is unconditional and the skill is identical
across repos. Missing or malformed config is discovered at run
time by the agent following the skill's instructions, where the
error message is actionable in the right context.

### 6. Implementation order

Three commits in this repo, each independently reviewable:

1. **`/navigate-specs` + per-skill placeholder profiles** — adds
   the new template, extends `REGISTERED_INJECTABLE_SKILLS` with the
   `navigate-specs` entry, refactors `skill-install.ts` to declare
   per-skill discovery functions and per-skill placeholder
   allowlists. Refines the existing `specs.md` template to
   cross-reference `/navigate-specs`. Unit + integration tests for
   the new skill. ~300 LOC + tests.

2. **Orchestrator day-1 contact** — happens **outside** this repo,
   in `../<host-project>/orchestrator/<host-project>-orchestrator/`. Not
   a docdog commit; just the place where commit (1)'s output meets
   real content. Includes the migration of TASK-043, TASK-046, and
   TASK-052's legacy BACKPORT entries.

3. **`/backport` skill + `backport:` config schema** — adds the
   third template (generic, same placeholder profile as
   `navigate-specs`) and the `backport:` block schema in
   `src/types/config.ts`. No discovery function, no install-time
   validation, no `{{routing_table}}` renderer. Tests cover:
   template renders with only version+timestamp; the schema type
   accepts the expected shape; placeholder allowlist rejects any
   per-repo placeholder accidentally added to the template. ~150
   LOC + tests. Lands **after** commit (2) so the orchestrator
   workflow exists and the skill's prose can reference a concrete
   live config block by name.

The proposal is delivered across two docdog-repo commits sandwiching
one orchestrator-repo commit. Each docdog commit is small,
self-contained, and ships independently to npm linkers.

### 7. Task folder lifecycle (no change from existing orchestrator)

The orchestrator's existing `/finalize-task` behavior is preserved
verbatim: task folders are created at task start, populated by
skills during the task, and **deleted** by `/finalize-task` after
artifact promotion and (in the new model) backport processing. Git
history is the canonical retention mechanism for completed task
content.

This means:

- **docdog's `tasks` collection holds only active tasks** — vertices
  appear when a task folder is created, disappear when `docdog index`
  runs after `/finalize-task` deletes the folder (existing soft-delete
  semantics under DD-049).
- **Completed task content is reached via git history.** The
  `/navigate-specs` skill teaches the retrieval recipe explicitly so
  no agent has to derive it.
- **No `tasks/archive/` directory.** No "private task collection"
  in docdog. Existing orchestrator behavior is non-disruptive
  precisely because we're not asking it to change.

### 8. Future work — git-history backfill

Captured here so it doesn't get forgotten: at some point the docdog
graph could be populated with **historical task content** by walking
`git log --diff-filter=D` for `tasks/TASK-*/` deletion commits,
retrieving each task's last-known content from the parent commit,
and ingesting as vertices in a separate `historical_tasks`
collection (or similar). This would give docdog full graph context
for completed work without changing the orchestrator's existing
folder-deletion behavior.

This is a one-off batch-ingest tool, not an ongoing process. It
lives in `.docdog/scripts/` of whichever repo runs it, reads git,
writes vertices, exits. Not in scope for PROPOSAL-020 — listed here
because the conversation that produced this proposal flagged it as
the natural next step once the active-tasks loop is solid.

### 10. Not in scope

- **Other injectable skills** beyond the three named here. Future
  candidates (e.g. `/tasks`, `/decisions`, `/release-notes`) are
  one-line additions to the registry plus a template; deliberately
  deferred until dogfood produces a concrete need.
- **`tasks/archive/` directory** or any persistent on-disk retention
  of completed task folders. Existing orchestrator behavior wins.
- **docdog `historical_tasks` collection** populated from git history.
  Captured as future work above.
- **`id_pattern` field on `dd_collection_meta`.** Still deferred from
  PROPOSAL-019; empirical prefix discovery still wins.
- **Auto-regeneration of injectable skills on `docdog index`.** Still
  explicit per PROPOSAL-019; agent-visible writes pass through git
  review.
- **The actual backport-processing workflow and script** — those
  live in the host repo (the orchestrator), not in docdog. PROPOSAL-020
  defines the skill that *describes* them; authoring them is
  orchestrator-side work.
- **Migration of legacy `LAST-BACKPORT` / `VERSION` / `MANIFEST-HASH`
  / `EXCHANGE-SUMMARY` files** from `specs/upstream-context/`. The
  orchestrator-side day-1 commit handles that as part of the
  ceremony cleanup. Not a docdog feature.
